Running log of milestones, bugs, and findings as the project develops.
Each entry should capture: what happened, what we learned, and what
(if anything) changed in the code as a result. This is raw material —
the README gets written FROM this, not the other way around.

Built the initial end-to-end skeleton: pose estimation (MediaPipe) →

## Entry 2 — MediaPipe 1.0.0 breaking change
**Date:** Week 1, Day 1 (setup)

**What happened:** Fresh `pip install mediapipe` pulled version 1.0.0,
which replaced the legacy `mp.solutions` API with a new "Tasks" API.
Our `pose_estimation.py` was written against `mp.solutions.pose`, so
every run crashed immediately with:
```
AttributeError: module 'mediapipe' has no attribute 'solutions'
```

**Finding:** `requirements.txt` had an unpinned `mediapipe>=0.10.9`,
which is exactly the kind of thing that silently breaks a working
project months later when a dependency ships a major version bump.

**Fix:** Pinned `mediapipe==0.10.21` in `requirements.txt`, the last
version before the Tasks API migration, with a comment explaining why.

**Takeaway for README:** worth a line about dependency pinning
discipline — this is a real production lesson, not just a personal
setup hiccup.

## Entry 3 — First real run: fall not detected (cam0)
**Date:** Week 1, Day 2

**What happened:** Ran the pipeline on `fall-01-cam0.mp4` from the
UR Fall Detection Dataset. Pipeline completed cleanly (160 frames
processed, CSV + annotated video written), but **no fall alert fired**
despite the clip containing a real fall.

**Investigation:** Inspecting the CSV around the fall:
- Frame 114: torso_angle=81.2°, hip_velocity=1.04 → correctly crossed
  both thresholds, `impact_detected` fired.
- Frames 116–121: pose landmarks missing entirely (MediaPipe lost
  tracking right at the moment of impact — common, expected).
- Frame 122: landmarks reappear, but torso_angle reads **8.9°** — a
  single anomalous low reading. Our recovery logic treated this as
  "person got back up" and reset state to `normal` on ONE frame.

**Root cause (deeper):** the low angle wasn't just noise — it was
sustained for many subsequent frames too. This is a genuine limitation
of 2D single-camera pose angle: when a fall happens roughly *along*
the camera's viewing axis (toward/away from camera) rather than across
it, the projected shoulder-hip line can foreshorten and no longer
reads as "horizontal" even though the person is fully down.

**Fix (two parts):**
1. Added debounce — "recovery" now requires 5 consecutive low-angle
   frames, not one, before resetting state.
2. Added a second, independent confirmation signal: **post-impact
   stillness**. If hip vertical velocity stays near-zero
   (`< 0.2` units/sec) for 4 consecutive frames after an impact, we
   confirm the fall regardless of what torso_angle says. A person who
   actually fell typically stops moving; this doesn't depend on the
   angle measurement at all, so it's immune to the foreshortening
   problem above.

**Result after fix:** replayed the same clip's data through the
patched detector — `fall_confirmed` correctly fires at frame 127,
confidence 0.95, and stays confirmed for the rest of the clip.

**Takeaway for README:** this is the single best "here's a real bug I
found and fixed" story in the project. Good interview material —
shows understanding of camera geometry limitations, not just
plugging in a library.

## Entry 4 — Same fall, second camera angle: total miss (cam1)
**Date:** Week 1, Day 2

**What happened:** Ran the identical pipeline (post-fix) on
`fall-01-cam1.mp4` — same fall event, same timestamp, filmed from a
second physical camera angle (UR Fall dataset ships synchronized
dual-camera footage). Result: **`state` stayed `normal` for all 160
frames.** No impact ever detected, let alone confirmed.

**Investigation — comparing peak values across both cameras:**

| Signal | Cam0 peak | Cam1 peak | Threshold |
|---|---|---|---|
| torso_angle | 89.5° | 34.8° | 60° |
| hip_velocity | 1.04 | 1.19 | 0.8 |
| aspect_ratio | 0.96 | 0.34 | — |

Hip velocity alone clears the threshold comfortably on cam1 (multiple
frames >0.8, peak 1.19) — the downward motion is real and strongly
detected. But torso_angle never comes close to 60°, and aspect_ratio
never rises above 0.34 (should approach/exceed 1.0 for a "wide, short"
fallen silhouette). Both shape-based signals stay in "standing" range
the entire clip.

**Root cause:** cam1 is positioned such that this particular fall
happens more toward/away from the camera than sideways across it —
the same foreshortening issue from Entry 3, except this time it
corrupts the *initial impact detection*, not just the recovery check.
Since our impact trigger requires BOTH angle AND velocity to cross
threshold simultaneously, and angle never does, the detector never
even leaves the `normal` state — so the stillness fallback (which only
activates post-impact) never gets a chance to run either.

**Fix:** none applied yet — this is a genuine architectural limitation,
not a quick threshold tweak. Logged here as v2 scope.

**Takeaway for README:** this is strong, quantified evidence for why
single fixed-camera 2D fall detection has a fundamental reliability
ceiling — the exact same real-world event was correctly caught by one
camera and completely missed by another, using identical detection
logic. Justifies multi-camera fusion (or velocity-only fallback
triggers) as a v2 priority, not just a "nice to have."

**Ideas for v2, to evaluate:**
- Multi-camera fusion — combine confidence scores from multiple
  camera angles, weighted by which camera has cleaner/more decisive
  signal at that moment.
- Velocity-only trigger path — allow impact detection to fire on a
  strong velocity spike alone (without requiring angle), falling back
  to the stillness signal for confirmation. Would need false-positive
  testing against non-fall clips (e.g. someone jogging/sitting fast)
  to check this doesn't hurt precision.

## Entry 5 — Batch runner built; local files went out of sync twice; first push
**Date:** Week 1, Day 3

**What happened:** Built infrastructure to test multiple clips at once
instead of running one video at a time by hand: `src/batch_runner.py`
reads `data/labels.csv` (clip name → expected `fall`/`no_fall`), runs
the full pipeline on every listed clip, and writes one `summary.csv`
scoring every result — plus still writes a full per-clip CSV log each
time, same as before, so individual bugs stay debuggable.

Also decided to stop shipping the project as a single zip and instead
share individual files as they're built/changed — closer to how a real
repo evolves file by file.

**What went wrong (twice):** after adding `run_pipeline.py`'s `run()`
signature change (needed so batch_runner could get results back as
data instead of only printed text) and separately after the earlier
`fall_detector.py` stillness-signal fix, the local project fell out of
sync with what had actually been designed/tested. Two real incidents:

1. First batch run crashed immediately:
   `TypeError: run() got an unexpected keyword argument 'quiet'`
   — the local `run_pipeline.py` was still the old version; the
   updated one had been described and tested but never actually
   handed over as a file to save locally.
2. After fixing that, the batch run completed but scored
   `fall-01-cam0` as a MISS — which contradicted Entry 3, where we'd
   already proven this exact clip gets caught after the stillness-fix.
   Same root cause: local `fall_detector.py` was still the pre-fix
   version.

**Root cause (general):** any time a fix is designed and verified by
testing code in an assistant sandbox, but not explicitly re-delivered
as a file, the person's local project silently stays on the old
version — and it can *look* like it's working (no errors) right up
until a test result contradicts an earlier documented finding.

**Fix:** did a manual file-by-file audit — listed every file delivered
across the whole conversation, and used `findstr`/`type` on the two
files not recently re-verified (`pose_estimation.py`, `features.py`)
to confirm their content matched what was expected, before trusting
any further test results.

**Result:** after replacing both outdated files, batch runner produced
the CORRECT, expected result:
```
fall-01-cam0: expected=fall detected=fall ✓
fall-01-cam1: expected=fall detected=no_fall ✗ MISS   (expected — see Entry 4)
RESULTS: 1/2 correct (7 skipped — clips not downloaded yet)
```

Also completed first `git init` → `git add .` → `git status` safety
check (confirmed `venv/`, `.mp4` files, and `__pycache__/` were all
correctly excluded per `.gitignore`) → committed → pushed to GitHub
successfully. Repo is now public and under version control.

**Takeaway for README:** two things worth a line each —
1. The batch runner itself (multi-clip testing + summary scoring) is
   a real feature worth describing, not just a testing convenience.
2. Worth being explicit in the repo about the workflow discipline of
   verifying local files against intended changes before trusting a
   test result — small thing, but it's the kind of "I check my own
   work" habit that's easy to claim and rare to actually demonstrate
   with a real example.

## Entry 6 — Second fall clip missed entirely: velocity/angle timing bug (cam0)
**Date:** Week 1, Day 4

**What happened:** Ran `fall-02-cam0.mp4` through the pipeline. Same
symptom as the very first cam0 run — pipeline completed cleanly
(110 frames), but `state` stayed `normal` for the entire clip. No
impact ever detected.

**Ground truth (confirmed by watching the actual video, not just the
CSV):** subject starts seated on the right side of frame, slowly leans
forward, **knees hit the ground first**, then the rest of the body
follows and collapses down. Not a straight topple — a two-stage
kneel-then-collapse fall.

**Investigation:** the CSV showed both signals working correctly, just
never overlapping:
- Frame 65: `hip_velocity = 0.86` (clears 0.8 threshold) —
  `torso_angle = 41°` (nowhere near the 60° threshold yet). This is
  the lean-forward still in progress.
- Frame 75: `hip_velocity = 0.85` (clears threshold again) —
  `torso_angle = 53°`. Almost certainly the knees making contact —
  a sudden downward motion of the lower body, measured at the hip.
- Frame 81: `torso_angle = 89.6°` (fully horizontal — body has now
  collapsed onto the ground) — but by now `hip_velocity = 0.28`,
  well under threshold. The knee-impact's velocity spike has already
  faded by the time the torso finishes going down.

**Root cause:** the impact trigger required
`hip_velocity >= threshold AND torso_angle >= threshold` on the exact
same frame. This fall has two distinct physical sub-events roughly
12-16 frames apart (knee impact, then torso collapse) — the velocity
spike belongs to the knees landing, the angle threshold gets crossed
later by the torso finishing its collapse. Requiring both
simultaneously misses this shape of fall entirely, even though both
signals independently behaved exactly as expected.

Broader implication: hip-velocity alone is really a proxy for
"the body's center of mass is dropping fast" — it doesn't distinguish
which body part initiates ground contact. A kneel-first fall (common
in real elderly fall scenarios — reaching for something, losing
balance while seated or near a chair) has a meaningfully different
velocity/angle signature than a straight topple.

**Fix:** replaced the same-frame requirement with a sliding window.
A velocity spike is now "remembered" for `velocity_spike_window_frames`
(20 frames, ~0.6s) after it happens. If the angle threshold gets
crossed any time within that window — even many frames after the
velocity spike itself has faded back down — it still counts as a
valid impact. Added as `velocity_spike_countdown` in `fall_detector.py`,
tracked before the missing-landmark early-return so an occlusion gap
can't erase the memory of a real spike.

**Result:** re-ran the same clip post-fix —
`[ALERT] Fall confirmed at frame 87 (t=2.90s, confidence=0.95)`.
Also regression-tested against the already-solved `fall-01-cam0` case
to confirm the fix didn't reintroduce the earlier bug — still confirms
correctly.

**Takeaway for README:** this is a different CLASS of bug than Entry 3.
Entry 3 was about measurement RELIABILITY (the angle number itself was
misleading due to camera geometry). This one is about event TIMING —
both measurements were accurate, but the detection logic assumed two
signals from the same fall would always co-occur on the same frame,
and a real, common fall pattern (kneel first, body follows) proved
that assumption wrong. Good example of the difference between "the
sensor lied" bugs and "the model of the physical world was too
simple" bugs — worth naming that distinction explicitly in the README.

## Entry 7 — Overhead camera breaks the feature basis entirely (fall-02-cam1)
**Date:** Week 1, Day 4

**What happened:** Ran `fall-02-cam1.mp4` — same fall event as Entry 6
(fall-02-cam0, the kneel-then-collapse fall), second camera angle.
Result: no alert, `state` stayed `normal` for all 110 frames.

**Ground truth (confirmed by watching the video):** cam1 for this
clip is mounted **directly overhead**, centered on the seated subject
— not a second side-on angle like fall-01's dual cameras. Subject
goes straight down naturally: knees drive into the ground first,
hands connect, then subject rolls onto their side.

Visually confirmed with two frames: pre-fall (subject seated, seen
as a top-down view of head/shoulders with no visible "upright vs.
tilted" cue at all) and post-fall (subject sprawled flat on the floor
next to the chair, body visibly larger/closer to the camera rather
than shifted in any particular vertical image direction) — matches
the root cause below exactly. Also worth noting: the dataset's cam1
feed is a depth camera (paired depth + RGB, split-screen), not RGB
alone — a real overhead solution would likely lean on the depth
channel rather than forcing 2D RGB pose estimation from a bad angle.

**Investigation:** the CSV showed a DIFFERENT failure pattern than any
previous entry:
- `torso_angle` reads 55°-90° from frame 14 onward (`t=0.47s`) — while
  the subject is still normally seated, per ground truth. A seated
  person should read well under our 60° fall threshold; instead the
  angle is already in "fallen" range almost from the start of the clip.
- `hip_velocity` never crosses the 0.8 threshold anywhere in the whole
  clip — peaks around 0.5-0.7 (vs. 0.85 on cam0, same fall, same
  moment). The one signal that DID work on fall-02-cam0 is muted here.

**Root cause — different in kind from every previous entry:** cam0's
issues (Entries 3, 4, 6) all involved a side-mounted camera at an
imperfect angle or with imperfect timing — the FEATURES still meant
what we intended, just imperfectly measured. This is different:
`torso_angle` and `hip_velocity` are both defined assuming a roughly
side-on (profile) camera:
  - `torso_angle` = angle of the 2D shoulder-hip vector from vertical,
    IN IMAGE SPACE. From directly overhead, this vector no longer
    represents torso tilt at all — it reflects which way the shoulders
    happen to be rotated in the horizontal plane. A seated person can
    read "high" purely from posture/orientation, unrelated to falling.
  - `hip_velocity` = vertical (y-axis) pixel movement over time. From
    a side camera, falling = moving toward the floor = increasing y =
    clean signal. From overhead, falling toward the floor means moving
    TOWARD the camera (getting closer/larger), not up/down in frame.
    The muted y-motion we do see is likely just the body's horizontal
    spread during knee/hand/side contact — a side effect of the fall,
    not a direct measurement of it.

This is not "harder to detect from this angle" (Entry 4's finding) —
it's "these specific features don't describe falling at all from this
camera type." The feature basis itself assumes a viewing geometry that
doesn't hold for an overhead mount.

**Fix:** none applied — this is real architectural scope, not a
threshold or windowing fix like Entries 3/6. Logged as v2/v3 territory.

**Result:** confirmed miss, root cause understood and distinct from
all prior entries. No code changes this entry.

**Takeaway for README:** this is the strongest limitations finding so
far, and worth its own callout — real fall-detection deployments
(senior care facilities, hospitals) commonly use CEILING-MOUNTED
cameras for full-room coverage, so this isn't a hypothetical edge
case. A production version would need either (a) an entirely different
feature set for overhead views (e.g. 2D bounding-box area/shape change,
motion blob dispersal, distance-from-center-of-room), or (b) a
per-camera "viewing geometry" config so the system knows which feature
set to apply based on how each camera is mounted. Good evidence this
project understands camera geometry isn't a detail — it's a first-order
design constraint.

**Ideas for v2/v3, to evaluate:**
- Overhead-specific feature set: bounding-box area (a body lying flat
  occupies more 2D area from directly above than a seated/standing
  body), aspect ratio behavior likely differs too and would need
  re-deriving from overhead data specifically.
- Per-camera config: store camera mount type (side / overhead / angled)
  alongside each camera's stream, route to the appropriate feature
  extractor rather than assuming one universal feature set.

## Entry 8 — "Good" camera fails too: it's trajectory, not camera number (fall-03-cam0)
**Date:** Week 1, Day 5

**What happened:** Ran `fall-03-cam0.mp4` (215 frames, ~7.2s). No
alert. Unlike prior misses, `torso_angle` never rose above ~12° for
the ENTIRE clip — no partial rise, no delayed catch-up, nothing close
to the 60° threshold at any point.

**Ground truth (confirmed by watching the video, 3 frames sampled):**
subject starts near the door at the back of the room and walks
STRAIGHT TOWARD the camera for the first ~6 seconds. Falls around
`t=6s`, ending up lying on the ground with the body oriented
toward/away from the camera (legs extending toward the lens), not
sideways across the frame.

**Investigation:** there IS a real, strong velocity spike — frame 171
(`t=5.7s`), `hip_velocity=1.18`, well above the 0.8 threshold — timing
lines up with the fall visible around `t=6s` in the sampled frames.
But `torso_angle` at that same moment is only 5.9°, and never
approaches 60° before or after. The Entry 6 velocity-window fix has
nothing to "catch" here, because angle simply never gets close enough
for the window to matter.

**Root cause — this is cam0, the "good" camera, exhibiting cam1's
exact Entry 3/4 weakness:** the subject's walking path put them
moving TOWARD cam0 for the whole clip, and the fall itself continued
along that same line (body ending up oriented along the camera's
viewing axis rather than across it). This is the same foreshortening
mechanism as Entry 3/4 — but it corrects an implicit assumption from
those earlier entries. Entry 4 was written as "cam0 catches falls,
cam1 misses them" — framed around WHICH camera. This clip proves that
framing was incomplete: cam0 fails here for the identical geometric
reason cam1 failed in Entry 3/4. **Reliability depends on the fall's
direction relative to a given camera's viewing axis, not on which
numbered camera is doing the recording.** Any fixed camera has a
"bad" trajectory range; which trajectories are bad just depends on
where that camera happens to be positioned in the room.

**Sharper architectural insight, generalized across Entries 3/4/7/8:**
`torso_angle` is not just one of two signals we weigh — it's a hard
GATE. The state machine can only leave `normal` and enter
`impact_detected` if angle crosses the 60° threshold. Even the
Entry 6 fix (velocity spike remembered across a window) still requires
angle to eventually cross threshold within that window — velocity
alone, however extreme, can never trigger detection by itself under
the current design. Every angle-based miss so far (Entry 4's cam1,
Entry 7's overhead cam1, and now this frontal fall-03-cam0) fails for
DIFFERENT underlying geometric reasons, but they all fail through the
SAME single point of failure: the angle gate never opens.

**Fix:** none applied — same as Entry 4/7, this is architecture-level,
not a threshold tweak. But this entry upgrades the priority of an idea
already logged in Entry 4 ("velocity-only trigger path") — with three
independent angle-gate failures now on record, a velocity-only fallback
path isn't just a nice-to-have, it looks like the single highest-value
v2 change: allowing a sustained/strong-enough velocity spike to trigger
`impact_detected` on its own (likely needs a stricter velocity
threshold than the current combined-signal one, to avoid false
positives from fast sitting/bending), independent of what angle is
doing. That would directly catch this clip, Entry 4's cam1 miss AND
Entry 7's overhead miss simultaneously — since velocity1.18, well
above threshold, was actually correct in ALL THREE of those cases;
angle was the common failure point every time.

**Result:** confirmed miss, root cause understood, and reframes Entry 4
more accurately. No code changes this entry — logged as the strongest
case yet for the velocity-only fallback path.

**Takeaway for README:** this is the entry that ties the whole
limitations story together. Don't describe it as "camera 0 works,
camera 1 doesn't" (inaccurate, per this entry) — describe it as
"single fixed 2D cameras have a trajectory-dependent blind spot, and
our angle-gated detection logic is a single point of failure across
every instance of that blind spot found so far." That's a much
stronger, more accurate systems-level insight than a per-camera
scorecard, and it directly motivates the velocity-only fallback as
next architecture work, not just multi-camera fusion.

## Entry 9 — Noisy, high-dropout tracking points to another steep-angle camera (fall-03-cam1)
**Date:** Week 1, Day 5

**What happened:** Ran `fall-03-cam1.mp4` (same fall as Entry 8,
second camera angle). No alert fired. Unlike prior entries, the
diagnosis here was made directly from the CSV pattern, without first
pulling reference frames from the video — worth noting because the
pattern was recognizable from data alone once compared against
earlier entries.

**Investigation — two patterns stood out, both different from any
previous clip:**

1. **Dropout rate far higher than normal, and NOT clustered around
   the fall.** Roughly a third of all 215 frames have no landmarks at
   all. Entry 3's dropout (fall-01-cam0) was a tight cluster of ~6
   frames right at the moment of impact — expected, since hitting the
   ground is when tracking is hardest. Here, large gaps appear
   throughout the ENTIRE clip, including early sections that should
   be calm standing/walking (e.g. frames 43-54 almost entirely blank).
   This points to unstable tracking for the whole feed, not just a
   fall-related occlusion.

2. **Values that do come through are erratic, not smooth.** Frames
   78-83: torso_angle jumps 22.4 -> 14.6 -> 14.5 -> 52.5 -> 22.8 ->
   10.6 across six consecutive frames (0.2s) — swings far too fast to
   reflect real body movement. Every previous entry's angle curve
   (even the wrong ones, like Entry 4/7) moved smoothly frame to
   frame; this one doesn't.

**Root cause (inferred, not yet visually confirmed):** this pattern
doesn't match Entry 3/4/8's category (smooth, foreshortening from a
side-mounted camera at a bad trajectory angle). It matches Entry 7's
category instead — MediaPipe's pose model, trained mostly on
frontal/side human imagery, struggling with a steep or overhead
viewing angle. Entry 7 showed that failure mode as smooth-but-biased
readings (angle reading falsely high, but SMOOTHLY so). This clip
suggests the same underlying cause (non-frontal camera geometry
confusing the pose estimator) can also manifest as outright unstable,
noisy, high-dropout tracking instead of a smooth bias — likely
depending on exact mount angle/distance/lighting. Best working
hypothesis: fall-03-cam1 is another steep-angle or overhead mount,
similar in category to fall-02-cam1 (Entry 7), just with worse
tracking stability than that clip had.

**Fix:** none applied — diagnosis only, consistent with Entries 4/7/8.

**Result:** miss confirmed, plausible root cause identified from log
patterns alone. Visual confirmation (reference frames from the actual
video) not yet done for this specific clip — flagged as a follow-up
if a firmer conclusion is needed, e.g. before finalizing the README's
description of this clip specifically.

**Takeaway for README:** supports the same overhead/steep-angle
limitation from Entry 7 with a second, independent data point — but
also demonstrates that this limitation doesn't always look the same
in the data (smooth-and-biased vs. noisy-and-dropout-heavy), which is
itself a useful nuance: detecting "this camera angle is unreliable"
automatically (e.g. via dropout rate or frame-to-frame value
volatility as a health-check signal) could be a legitimate v2 feature
in its own right — flagging a bad camera feed rather than silently
producing wrong fall/no-fall answers from it.

## Entry 10 — Design proposal: automatic camera-viewpoint health check
**Date:** Week 1, Day 5

**What happened:** No new clip run this entry — this is a design idea
captured before building anything, connecting threads from several
earlier entries.

**The idea:** right now the pipeline has zero awareness of camera
geometry — it applies the same `torso_angle`/`hip_velocity` logic
regardless of whether the camera is a reliable side-on view or a
problematic overhead/steep one. Every camera-geometry diagnosis so
far (Entries 4, 7, 8, 9) has been done manually, by a person watching
the actual footage and describing it. Proposal: build an automatic
"viewpoint health check" that runs on each camera BEFORE trusting its
angle-based signal, using statistical fingerprints we've already
observed by hand:
  - **Resting baseline angle** — a normal standing person should read
    torso_angle near 0-10° (confirmed on fall-04-cam0's t=0 frame:
    7°). An elevated resting baseline (fall-04-cam1 started at 59°;
    fall-02-cam1, Entry 7, stayed 55-90° throughout) signals the
    side-on assumption doesn't hold for this camera.
  - **Frame-to-frame volatility** — normal clips show smooth angle
    curves frame to frame. Entry 9 (fall-03-cam1) showed swings like
    22°→52°→22° across consecutive frames — far faster than real body
    movement allows.
  - **Landmark dropout rate** — Entry 9 also showed ~1/3 of frames
    with no landmarks at all, spread through the WHOLE clip rather
    than clustered at impact (contrast with Entry 3's ~6-frame
    impact-only gap on an otherwise reliable camera).

If a camera fails this check, the system would either (a) reduce
confidence scores generally, or (b) lean more heavily on
`hip_velocity` alone (which has held up more consistently than angle
across every entry so far — even Entry 8's frontal-fall miss had a
correct, strong velocity spike) rather than requiring the angle gate
to open at all.

**Why this matters / what it connects:** directly builds on Entry 8's
already-flagged idea (velocity-only fallback path) by adding the
missing piece — WHEN to trust velocity-only vs. requiring the full
angle+velocity combination. Without a health check, a velocity-only
fallback risks more false positives on GOOD cameras; with one, it
only kicks in for cameras that have already been statistically
flagged as unreliable.

**Fix:** none yet — this is a design proposal only, not implemented.
Deliberately logged before prototyping, per team discussion, to
decide whether more data is needed first (see next entry / decision
below) before committing to specific thresholds.

**Open question flagged before building:** current "bad camera"
examples number only 2-3 (fall-02-cam1, fall-03-cam1, and
fall-04-cam1 pending visual confirmation of its actual geometry) —
and even those don't share one clean signature (Entry 7 = permanently
elevated; Entry 9 = noisy/high-dropout; fall-04-cam1 = a third,
not-yet-confirmed shape). Risk of designing thresholds that overfit
to 2-3 anecdotes rather than a real general pattern. Decision: gather
a few more clips specifically to build out a small "camera profile"
dataset (contrasting known-good vs. known-bad cameras) before
finalizing any hard thresholds for this check.

**Takeaway for README:** this is a strong "here's the natural next
architectural step, and here's why we deliberately didn't rush into
building it without enough data" story — shows engineering judgment
about when to gather more evidence vs. when to start building,
not just a list of fixes.

## Entry 11 — Normal-at-rest camera still misses: corrects Entry 10's design
**Date:** Week 1, Day 6

**What happened:** Ran `fall-05-cam1.mp4`. No alert. But this miss
looks fundamentally different from Entries 7/9's cam1 failures, and
it exposes a real gap in the Entry 10 design proposal.

**Investigation:** resting baseline (most of the clip before the
fall) sits in a completely normal range — torso_angle mostly 0.3°-3°,
matching fall-05-cam0's healthy baseline closely. No elevated
starting angle (unlike Entry 7), no excessive scattered dropout or
wild frame-to-frame jitter (unlike Entry 9). By every Entry 10
health-check criterion, this camera would have been judged RELIABLE.

But during the fall itself (frames 100-115, t=3.3-3.6s), hip_velocity
spikes repeatedly and strongly — 1.05, 1.29, 0.96, 1.05, 0.89, 1.10,
all comfortably above the 0.8 threshold, multiple times in a row.
torso_angle during that same window only climbs to 20-25°, and never
exceeds ~32° anywhere in the entire clip (frame 147, near the end).
Velocity is unambiguous; angle never gets remotely close to the 60°
gate.

**Root cause:** this matches Entry 8's category, not Entry 7/9's —
the fall's direction of travel happens to run along this camera's
viewing axis (same foreshortening mechanism as fall-03-cam0), even
though the camera's baseline/resting behavior is completely healthy.

**Why this corrects Entry 10:** Entry 10 proposed a health check based
on calibrating each camera ONCE, at rest, before trusting it. This
entry proves that approach has a blind spot — it can only catch
cameras that are broken all the time (Entry 7/9's category). It
CANNOT catch a camera that behaves perfectly at rest but fails for a
specific fall's trajectory (Entry 8/11's category), because trajectory
-dependent failure is invisible until an actual fall happens along the
bad axis. A one-time rest calibration would have given this camera a
clean bill of health right before it silently missed a real fall.

**Fix:** none applied. This changes what Entry 10 needs to become —
noted below.

**Result:** miss confirmed. More importantly: proof that "is this
camera generally reliable" and "will this camera catch THIS fall" are
two different questions, and a design that only answers the first one
provides false confidence, not real safety.

**Takeaway for README / revised v2 direction:** the corrected design
insight is that camera reliability isn't a fixed property of a
camera — it's dependent on the interaction between camera position
and fall direction, which can't be fully known in advance. This
argues MORE strongly for Entry 8's velocity-only fallback path (since
velocity was correct here, same as Entry 8, even though angle-based
health-checking couldn't have caught this case) and suggests Entry
10's health check is still useful for the Entry 7/9 category of
failure, but needs to be explicitly scoped as "catches broken-camera
misses, does NOT catch trajectory misses" rather than implied as a
general reliability solution. Two different problems, two different
mitigations — conflating them would have shipped a false sense of
coverage.
